# Synthetic Benchmark で分かったこと（現行 main のベースライン）

`evaluation/` の Synthetic Benchmark を **100ケース × 4通り = 400ラン**（約160秒）回して得た観測。
**productionアルゴリズムは一切変更していない。** 以下は「修正提案」であって修正済みではない。

計測条件: 手続き生成の目元 320×240 × 12枚、手続き生成の商品まつ毛1種、既定パラメータ
（`fg_thresh=0.70` / `bg_thresh=0.18` / `unknown_band_px=6`）、二値化 `alpha >= 0.5`。
再現は `evaluation/README.md` の手順。数値の意味と限界も同ファイルに書いてある。

## この文書の読み方（層の区別）

各節に **[A] / [B] / [C]** を付けている。`evaluation/README.md` §0 の分類と同じ。

- **[A] データセットに依存しないコードの事実** — 合成データではなくコードパスの性質を測っている。
  **実写でも同じことが起きる**ので、そのまま修正対象にしてよい
- **[B] 相対・頑健性の傾向** — 方向性は信頼できる。実写数枚での確認が望ましい
- **[C] 絶対スコア** — **実写性能を示さない**。回帰検出の基準値としてのみ使う。
  「本システムの精度は Dice 0.52」という引用は誤り

絶対値が低く出る主因はGTの粒度である（GTは毛1本単位で画像の3.4%しかない）。
人間は再合成結果を見て判断するが、この指標は毛1本の一致を見ており、両者は一致しない。
合成が実写より甘い点・厳しい点は両方向に同程度あり、`evaluation/README.md` §8 に列挙してある。

## 1. 自動推定は「取りこぼさないが、取りすぎる」 [B]

Recall 0.98 に対し Precision 0.36。予測面積はGTの **2.80倍**（中央値2.90倍。oracle brushでは1.08倍）で、
**毛と毛の間の肌までまつ毛として抽出している**
（`evaluation-results/cases/*/comparison_bare_auto.png` で目視確認できる）。

- 元画像に貼り戻す限りは肌の色が同じなので破綻しない（`reconstruction_error` は 16〜19 と小さい）
- しかし本来の用途は **AI加工後の別人の肌へ貼る**こと。取りすぎた肌が一緒に貼られるため、
  肌色が変わるとまつ毛の周囲に元の肌色のハローが出る。面積比2.8倍はその量を示している
- 原因の候補: `build_trimap` が `prob >= bg_thresh(0.18)` を `unknown_band_px=6` で膨張させて
  Unknown帯を作り、closed-form matting がその帯を埋めている

**Precision 0.36 という値そのものは合成条件依存（C層）である。** 手続き生成の商品は毛束の隙間が
実物より広いため、隙間の肌を拾うペナルティが実写より大きく出る。一方 **「過剰検出が起きている」
という事実と面積比のオーダー（2〜3倍）は B層** として扱ってよい。
実写での確認はマスクを描かずにできる（`evaluation/README.md` §8 末尾）。

**改善の優先度: 最高。** 実運用の見た目（ハロー）に直結するのはこの過剰検出である。

## 2. 未装着画像（Mode A）の効果がほぼ無い [B]

Dice 0.524（bare あり）vs 0.515（worn only）。差分マップ・landmark affine・ECC 一式を通しても、
暗部フォールバックとほぼ同じ結果しか出ていない。

- 位置ずれ 4px でも Dice は 0.505 で、ECC は破綻していない（＝アライメントの問題ではない）
- `difference_map` は `_norm_percentile(50, 99.5)` でROI内の分布に正規化するため、
  出力が「まつ毛らしさの絶対量」ではなく「ROI内での相対的な暗さ」になっている。
  暗部マップも同じ性質なので、両者が似た結果に収束していると考えられる
- 合成データの限界も効いている可能性がある（自まつ毛が独立レイヤーなので、実写ほど
  「装着で自まつ毛が動く」効果がない）。ただし *差分がある側が勝てていない* こと自体は観測事実

**示唆:** 「未装着画像を撮ってもらう」というUXコストに見合う利得が、現状の実装では出ていない。
差分の使い方（percentile正規化をやめる／差分を prior ではなく直接 trimap の FG 種に使う）を
見直す価値がある。

## 3. 理想ブラシで Dice 0.52 → 0.72、しかし 1.0 にはならない [B]

`oracle` 行は GT から作った3値ブラシを `build_trimap` に渡した結果で、trimap が完全に固定されるため
**matting 単体の性能**を表す（bare / worn_only の結果が一致するのはそのため）。

- Precision 0.36 → 0.75。**品質の大半はブラシ補正が担っている**という製品設計の裏付け
- 一方 Recall は 0.98 → 0.74 に下がる。closed-form matting は 1〜2px の毛先を
  `alpha >= 0.5` に持ち上げきれない。つまり **完璧な操作をしても毛先は薄くなる**
- したがって自動推定を改善する余地（0.52→0.72）と、matting自体の限界（0.72→1.0）は別問題

## 4. 最も崩れる条件は「JPEG圧縮」と「ピンぼけ」 [B]

条件別 Dice（bare/自動 → oracle）:

| 条件 | Dice (bare/自動) | Precision | Dice (oracle) |
| --- | --- | --- | --- |
| jpeg_quality 30/60 | **0.431** | 0.280 | 0.512 |
| realistic（ノイズ+JPEG+位置ずれ+影） | **0.437** | 0.283 | 0.571 |
| blur_sigma 1.0/2.0 | **0.476** | 0.317 | 0.609 |
| shadow 0.35 | 0.488 | 0.324 | 0.758 |
| brightness 0.7/1.3 | 0.491 | 0.326 | 0.796 |
| baseline | 0.512 | 0.345 | 0.769 |
| noise_sigma 3/8 | 0.527 | 0.359 | 0.841 |
| rotation ±5/±10° | 0.605 | 0.440 | 0.748 |

- **JPEG と blur は oracle でも回復しない**（0.51 / 0.61）。細い毛の情報が入力から失われており、
  閾値調整では戻らない。**「スマホで撮った圧縮画像」が最大のリスク**であり、
  運用面（撮影ガイド・高品質保存の要求）で対処すべき性質
- 影・明るさは oracle でほぼ回復する（0.76 / 0.80）→ 自動推定の evidence 段の弱さであって、
  情報が失われているわけではない
- 回転・反転は Dice が **上がる**。oracle は条件に依存しない（0.75前後で平坦）ので、これは
  精度向上ではなく **自動推定の過剰検出が減っただけ**。商品が目のライン・自まつ毛から離れると
  誤検出源が減る。つまり過剰検出の主因は「商品の姿勢」ではなく「目元の他の暗い構造」である
- 位置ずれ・ノイズでは大きく崩れない（ECC と percentile正規化が効いている）

## 5. Pixel Mutation: 補間の色誤差はどれも小さい [A]

### 5.1 `recompose_onto` がアルファ前乗算していない（実害は現状ほぼ無い）

`backend/lash_extraction/matting.py:77` は RGBA を **前乗算せずに** `INTER_LINEAR` で warp する。
alpha=0 の画素にも `estimate_foreground_ml` が何らかの色を置いているため、原理的にはそれが毛先に混ざる。
同じリポジトリ内の手動ROI経路 `SessionService._recompose_into_rect` は既に前乗算しており
（`docs/handover.md` L109「アルファ前乗算してから拡縮する（ハロー防止）」）、
**同じ問題への対策が landmark 経路にだけ入っていない**という不整合は事実である。

> **訂正（重要）**: 本文書の初版は「毛先のRGB誤差が30〜40倍」と書いていたが、これは**過大評価**だった。
> `evaluation/mutation.py` の合成実験が、透明部を **背景の肌色で埋める** 仮定を置いていたためである。
> 実際の `estimate_foreground_ml` の出力を測ると、透明部に残っているのは肌色ではない。

本番の `product_rgba` を実測した平均輝度:

| 領域 | FG推定が残している輝度 |
| --- | --- |
| alpha = 0（完全透明） | **86** |
| fringe（半透明帯） | 91 |
| opaque（まつ毛本体） | 60 |
| （参考）元画像の肌 | 178 |

つまり透明部の色は **肌（178）ではなく、まつ毛本体（60）に近い暗い値（86）** である。
混ざる色差が 26 程度しかないので、前乗算の有無で結果はほとんど変わらない。

**本番の product_rgba を使い、4倍スーパーサンプル合成を正解として比較した実測**
（8ケース平均、AIモデルの肌を+50明るくした＝差が最も出る条件、単位は0-255）:

| 変換 | 現行（非前乗算）の誤差 | 前乗算にした場合 | 改善 |
| --- | --- | --- | --- |
| 0.5px平行移動 | 0.416 | 0.180 | **+0.236** |
| 回転5° | 1.535 | 1.514 | +0.021 |
| 回転10° | 1.894 | 1.897 | **−0.004** |
| 拡大1.1× | 2.315 | 2.321 | **−0.006** |

**改善幅は最大でも 0.24/255 で、回転・拡大ではわずかに悪化することさえある**（前乗算→逆前乗算を
uint8 で往復する量子化誤差が、微小な色漏れの利得を上回るため。float で保持すれば消える）。
視認できる差ではない。

したがって前乗算の修正は **「正しさの整合（hygiene）」であって「画質改善」ではない**。
直しても見た目は悪くならないが、良くもならない。優先度は下げるべきである（§7）。

**ただし前提条件つきである。** 透明部が暗い値で埋まっているのは、現状のalphaが過剰検出で
広く取れており、`estimate_foreground_ml` がまつ毛周辺までまつ毛色として推定しているからである。
**§1の過剰検出を直すと透明部の色は肌に近づき、この色漏れが顕在化する可能性がある。**
順序は「過剰検出を直す → 前乗算の影響を再測定 → 必要なら前乗算を入れる」が正しい。

### 5.2 `exact_color_preservation_rate` は指標として弱い

| 変換 | linear（現行） | nearest | premultiplied_lanczos4 |
| --- | --- | --- | --- |
| 整数移動 | 1.000 | 1.000 | 1.000 |
| 0.5px移動 | 0.662 | 1.000 | 0.216 |
| 回転10° | 0.722 | 1.000 | 0.426 |
| 拡大1.1× | 0.711 | 1.000 | 0.386 |

`nearest` は色を100%保つが alpha Grad は 1.4〜2.4倍悪化する（1〜2px幅の毛束を間引くため）。
`lanczos4` は幾何が最良（alpha MAD 最小）だが色の変質は最大（リンギング）。
そして本番の affine は landmark から LMEDS で推定するので厳密な単位行列にならず、
**実運用で exact preservation が 1.0 になることはない**。

**示唆:** 「Level 3 = Pixel Preserve」を *ビット単位不変* と読むと静止画パスでは達成不可能。
「生成AIに描き直させない（再合成のみ）」という定義に文書上言い換えるべき。
補間による平均色誤差は 0.3〜0.6 LSB で無視できる水準であり、**変えるべきは前乗算（5.1）だけ**。

### 5.3 抽出前の ROI 縮小のほうが影響が大きい

`crop_roi` は ROI幅が `MAX_ROI_WIDTH=1100` を超えると INTER_AREA で縮小する。

| 縮小率 | exact preserved | RGB MAE |
| --- | --- | --- |
| 1.00（縮小なし） | 1.000 | 0.00 |
| 0.75 | 0.182 | 3.86 |
| 0.31 | 0.128 | 6.96 |

再合成時の補間（RGB MAE 0.4前後）より **1桁大きい**。実写の高解像度スマホ写真では必ず通る経路なので、
「商品ピクセルが変質する最大の場所は再合成ではなく抽出前のROI縮小」である。

## 6. 副次的に見つかった実装上の問題 [A]

1. **trimapにFGが無いと未処理の例外**: probability が一度も `fg_thresh` に届かないと
   `pymatting.trimap_split` が `ValueError: Trimap did not contain foreground values` を投げ、
   `/api/matte` は 500 になる（`backend/api/errors.py` に該当マッピングが無い）。
   平坦な画像や `−背景` だけ塗った状態で再現する。400/422 で返すべき
2. **pymatting の警告が全ランで出る**:
   `PERFORMANCE WARNING: Thresholded incomplete Cholesky decomposition failed ...` が
   毎回3回出る。Unknown帯が広いことと関係している可能性があり、精度以前に速度面の非効率
3. `roi_scale` が 1.0 でないケースでは、商品RGB誤差にROI縮小の再標本化が混ざるため
   fidelity 指標が単独では解釈できない（本Benchmarkは 1.0 に固定して測っている）

## 7. 次に改善するとしたら（優先順）

括弧内は「その判断の根拠がどの層か」。**A なら合成データの妥当性を待たずに着手してよい。**

1. **FG無しtrimapの例外を400/422にする**（根拠 **A**、低コスト）。§6.1。
   ユーザー操作で500が出る状態で、合成データの妥当性とは無関係に直せる
2. **過剰検出を下げる**（根拠 **B**、値そのものは C）。AI加工画像へ貼るときのハロー量に直結する
   **唯一の見た目要因**。`unknown_band_px` / `bg_thresh` の感度を条件別に測り、Unknown帯の作り方を
   見直す（膨張ではなく、勾配・線状性を使った帯にする等）。
   着手前に実写数枚で面積比を確認しておくと空振りしない（`evaluation/README.md` §8 末尾）
3. **入力品質のガード**（根拠 **B**）。JPEG圧縮とピンぼけは oracle でも回復しない。
   アップロード時に鮮鋭度・圧縮率を測って警告する運用側の対策が費用対効果が高い
4. **未装着画像の使い道を再設計する**（根拠 **B**、ただし合成では自まつ毛の絡みを再現できていないため
   実写で利得が出る可能性は残る）。現状 UX コスト（2枚撮影）に見合う利得が出ていない。
   percentile 正規化の見直し、または差分を trimap の FG 種として直接使う方向
5. **matting の毛先復元（0.72→）**（根拠 **C**）。ここから先はアルゴリズム置換（guided filter 系や
   学習ベース matting）の検討が必要で、優先度は上より下
6. **実写ケースでの検証。** 本Benchmarkは合成であり実写性能を証明しない。
   `worn/bare/gt_alpha` を持つ実写ケースを数枚作れば、同じ runner で同じ指標が出る。
   2・4 に本格着手する前にこれを済ませるのが理想
7. **`recompose_onto` のアルファ前乗算**（根拠 **A**、ただし実害は現状 0.24/255 未満 → §5.1）。
   コードの整合性としては直すべきだが、画質改善にはならない。**2 を直した後に再測定してから**
   判断する（過剰検出が減ると顕在化する可能性がある）。ついでに直す程度の位置づけ
